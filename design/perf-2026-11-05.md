## How it was measured

`tests/perf/perf_recorder.gd` (new) is added by either probe with `-- --profile`. Every frame it
records:

- the wall time, the `_process` pass, and the deferred redraw flush up to the last CanvasItem draw;
- the viewport's render CPU and GPU time;
- draw calls and node count;
- which frames handled a command.

It also attributes the draw flush to scripts: it counts each CanvasItem's `draw` signal and times the
gap before it, times container sorts, and accepts spans from temporary instrumentation. That
instrumentation was used in `CardWidget._draw` and `CardLayouts` and was not committed.

```
godot --path rldb --resolution 1600x1000 -s res://tests/perf/perf_run.gd -- --profile
godot --path rldb --resolution 1600x1000 -s res://tests/perf/qa_perf_soak.gd -- --profile
```

### What the profile showed (before)

- GPU time was about 0.3 ms and render CPU about 2 ms. `_process` was about 0.4 ms. **The cost was
  in the deferred redraw flush**: on average 27.7 ms of a 30 ms slow frame.
- **Card faces made up most of that flush.** One face paint costs 0.3 ms (an empty zone) to 2.5 ms
  (a hand card: gilded jewels, badges, text). Two patterns caused it:
  1. **Redundant repaints.** Each new view set every board and hand card up again, re-applied its
     marks, and called `w.queue_redraw()` unconditionally (`game_board_view._set_slot`). About 25 faces
     were repainted per command and about 75% of them were unchanged. That is 10-15 ms per command
     frame.
  2. **Scale animations.** Godot repaints a Control whenever its `scale` changes. The FX animate card
     scale: pulses, the hand's deal-in from 0.5, summon landings, and the board's camera shake.
     During the shake every card crossed the 1/64 text-oversampling step. So every animated frame
     repainted whole faces.
- The suspects named in the brief were not the main cost:
  - The cursor only calls `set_custom_mouse_cursor` when a shape's art changes (`CursorSkin.apply`
    compares tags).
  - Font fallback did not matter: turning `allow_system_fallback` off changed nothing (`--exp=nosysfb`).
  - Status FX, the vignette shader and full-screen rects cost under 0.3 ms a frame. GPU time stayed
    at about 0.3 ms throughout.

## Fixes (no visible change)

1. **A face repaints only when its inputs change** (`CardWidget.request_face` / `face_key`). The key
   is a hash of everything the face reads: the view, kind, size, orientation, hover, lift, combat
   preview, an empty zone's pick and dim, oversampling, reduced motion, and `face_epoch`. If the key is
   unchanged, only the state overlay repaints. `setup()` also skips rebuilding an unchanged tooltip.
   `CardWidget.face_epoch` forces a repaint after a global look change, such as a card back picked
   while cards are on screen.
2. **The face is on its own internal canvas item** (`_face`, under the overlay). A `scale` change on
   the widget now only moves it.
   - Text is re-rasterised at once when the on-screen scale jumps by more than 15 %.
   - A smaller change is re-rasterised once the scale has held still for 2 frames.
   - A shake or a pulse that returns to rest repaints nothing.
   - The child takes the widget's dim (`self_modulate`) and its dissolve or burn material
     (`use_parent_material`).
3. **Pixel parity is verified.** `src/dev/card_face_parity_shots.gd` renders a fixed sheet: every card
   kind and orientation, statuses, preview, dims, selection, ready, order badge, card back, set card,
   empty zones, a dissolve material, an FX scale and a hover lift. Comparing the old and new code gave
   147 px different, each by 1/255. Two runs of the same code differ by 176 px at 1/255, so the
   difference is GPU/MSAA noise. Sheets:
   - `production/qa/evidence/2026-11-05-l-batch/perf/card_face_before.jpg`
   - `production/qa/evidence/2026-11-05-l-batch/perf/card_face_after.jpg`

`reduce_motion` behaviour is unchanged: the overlays' processing rules were not touched.

## What is left

- **The soak's p95 (27.6 ms) is now set by command frames.** In that probe one frame in four handles
  a command, about four times faster than a human plays. A command frame runs the authority, both
  views and `GameScreen` render (p50 4.3 ms, p95 17 ms, unchanged), plus the faces that really
  changed. Frames without a command are at p95 11.2 ms. At human pace a command frame is rare, and
  `perf_run` at 6 frames per command reads p95 15 ms. A next step, owned by the engine programmer,
  would be the render path itself: the prompt banner, details pane and tooltip rebuilds per view.
- **Remaining per-frame ambient redraws:**
  - `PlayerPlate`'s breathing frame, about 0.65 ms per frame on the active plate.
  - `PhasePips`, which redraws all three capsules for one breathing glow, about 0.5 ms.
  - The ready-glow card overlays, about 0.25 ms each.

  They are small. Splitting their animated part onto its own layer (as `SeriesMedallion` does) would
  save about 1-2 ms a frame.
- **Card face paint cost itself** (about 2.4 ms for a hand card, spread over frame, jewels, badges,
  gem and text). The jewels could be recorded once per size into a `MeshPen`, as `ZoneMesh` does for
  zones. That would also cut the ~3,500 draw calls per frame.
